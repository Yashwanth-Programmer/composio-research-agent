04 — How the agent works

Pipeline, and where a human stepped in

Built on the Composio SDK for the search/fetch tool layer and Gemini for structured extraction and verdict reasoning. A targeted GitHub-assisted MCP verification pass was added after the first batch.

1
Batch dispatch
Each of the 100 apps is sent to the agent one at a time with a name, category hint, and a fixed schema to fill: auth methods, self-serve vs. gated, API surface, MCP existence, buildability verdict, and an evidence URL.
2
Tool-using research loop
The agent calls web search and page-fetch tools through Composio, reads official developer docs, and returns strict JSON — no free text, so 100 runs stay machine-comparable.
3
Human sampling (the honest part)
27 of the 100 rows were checked in the targeted MCP verification pass: 6 remained genuinely "no MCP" and 21 had credible MCP evidence, including community/third-party implementations.
4
GitHub-augmented rerun
The 27 MCP=false candidates were re-checked with additional search/GitHub evidence. 21 had MCP evidence; 6 remained false.
5
Pattern rollup
The auth, access, and buildability distributions remain from the completed first-pass dataset; the MCP verification findings are reported separately so they are not mixed into the original run.
04 — The proof

What is actually runnable

The repository contains the batch runner, structured output, analysis utility, and the interactive case study.

1
Draft research
python run_batch.py reads apps.csv, researches each app with Gemini + Composio Search, and appends one JSON object per app to results.jsonl.
2
Resumable output
Existing app names in results.jsonl are skipped, so the batch can resume after interruptions.
3
Targeted MCP verification
The MCP=false candidate set is re-checked with additional search/GitHub evidence instead of rerunning all 100 apps.
4
Pattern rollup
python analyze.py reads the results and generates the aggregate patterns used in the case study.
